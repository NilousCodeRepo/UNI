## Design overview (technical)
Use Views only to create and expose JavaFX Nodes (factory methods or getters). Use a Controller that composes Views, registers listeners/handlers, and invokes Model operations. Main must only bootstrap by creating the Controller and handing it the Stage. Keep responsibilities strict:

- View: construct visuals, expose nodes and minimal helper APIs (e.g., getRoot(), createButton(text)).
- Controller: composition, event wiring, input validation, navigation, calling Model methods, and transforming Model state to View updates.
- Model: pure state and business logic, observable where appropriate (JavaFX Properties) so Controllers can bind to them.

Below I expand on practical details, lifecycle, threading, testing, and API choices.

## Concrete view API recommendations
Make Views expose JavaFX types and be small, focused classes. Example design principles:

- Prefer factory methods over subclassing JavaFX classes unless you need new behavior.
- Expose read-only access to important nodes via getters (e.g., Node getRoot()).
- Avoid embedding event handlers or model code inside Views.
- Provide methods to set view-specific data (e.g., setTitle(String)) but do not call business logic.

Example (improved from your code):

Window.java
```
package view;

import javafx.scene.Scene;
import javafx.scene.layout.StackPane;
import javafx.stage.Stage;

public final class Window {
  private final StackPane root = new StackPane();

  public Window() {
    root.getStyleClass().add("root");
  }

  public StackPane getRoot() { return root; }

  public Scene createScene(int width, int height, String cssPath) {
    Scene scene = new Scene(root, width, height);
    if (cssPath != null) {
      scene.getStylesheets().add(getClass().getResource(cssPath).toExternalForm());
    }
    return scene;
  }

  // helper that configures stage without showing it (Controller decides when to show)
  public void applyToStage(Stage stage, int width, int height, String cssPath) {
    stage.setScene(createScene(width, height, cssPath));
  }
}
```

VButtons.java
```
package view;

import javafx.scene.control.Button;
import javafx.scene.layout.VBox;

public final class VButtons {

  public VBox createVBox(int spacing, String cssClass) {
    VBox v = new VBox(spacing);
    if (cssClass != null) v.getStyleClass().add(cssClass);
    return v;
  }

  public Button createButton(String text, String cssClass) {
    Button b = new Button(text);
    if (cssClass != null) b.getStyleClass().add(cssClass);
    return b;
  }
}
```

Notes:
- Keep packages lowercase (Java convention).
- Make classes final when not intended for extension.
- Return concrete JavaFX types so Controller can compose arbitrarily.

## Controller responsibilities and examples
Controller composes view parts, registers event handlers, converts Model state to UI, and vice versa.

Controller.java
```
package controller;

import javafx.stage.Stage;
import view.Window;
import view.VButtons;
import model.GameModel;

public class MainController {
  private final Window window = new Window();
  private final VButtons vbuttons = new VButtons();
  private final GameModel model;

  public MainController(GameModel model) {
    this.model = model;
    compose();
    wireModel();
  }

  private void compose() {
    var menu = vbuttons.createVBox(8, "menu");
    var start = vbuttons.createButton("Start", "btn");
    var exit = vbuttons.createButton("Exit", "btn");
    menu.getChildren().addAll(start, exit);
    window.getRoot().getChildren().add(menu);

    start.setOnAction(e -> onStart());
    exit.setOnAction(e -> onExit());
  }

  private void wireModel() {
    // example: bind a label to model property, or listen for changes
    // model.scoreProperty().addListener((obs, oldV, newV) -> updateScore(newV));
  }

  private void onStart() {
    model.startGame(); // controller triggers model action
  }

  private void onExit() {
    // controller decides navigation/exit
    System.exit(0);
  }

  public void show(Stage stage) {
    stage.setTitle("UNO the GAME");
    window.applyToStage(stage, 400, 300, "/styles/start_menu.css");
    stage.show();
  }
}
```

Why this is correct:
- Controller owns application flow and interactions.
- Views remain reusable and testable (they have no business logic).
- Model remains decoupled from JavaFX specifics (except when using Properties as a convenience).

## Model and binding: use JavaFX Properties where helpful
- Use javafx.beans.property.* for observable fields you want to bind to UI (StringProperty, IntegerProperty, BooleanProperty).
- Models that expose Properties enable Controller to bind directly for UI updates:
  - Simple binding: label.textProperty().bind(model.nameProperty())
  - Two-way binding: textField.textProperty().bindBidirectional(model.nameProperty()) — use sparingly for inputs.

Keep business logic pure (no Platform.runLater or UI code in Model).

## Threading and Platform.runLater
- All JavaFX scene graph operations must run on the JavaFX Application Thread.
- Long-running or blocking operations must run on background threads (Task, Service, ExecutorService).
- When background work completes and you need to update UI, use Platform.runLater(...) or updateTask’s message/progress bindings.
- Controller should spawn background tasks as needed and update model or UI via safe mechanisms:
  - model.updateFromBackground(result) where updateFromBackground uses Platform.runLater if it mutates observable properties consumed by UI.

Example Task usage:
```
Task<Result> task = new Task<>() {
  @Override protected Result call() { ... } // background work
};
task.setOnSucceeded(evt -> controller.onTaskResult(task.getValue())); // runs on FX thread
new Thread(task).start();
```

## Resource loading and CSS
- Use getClass().getResource("/path/to.css") and prefer absolute resource paths from classpath root (leading '/').
- Handle missing resource gracefully (check for null).
- Keep CSS class names consistent between Java code and .css file.

## Memory leaks and event listeners
- Remove listeners when Views are discarded (especially for long-lived model listeners).
- If Controller registers model listeners, ensure they’re removed when the controller/view is disposed (provide a dispose() method).
- Avoid anonymous inner listeners capturing heavy outer objects if lifecycle mismatch exists.

Example disposal pattern:
```
public void dispose() {
  model.nameProperty().removeListener(nameListener);
  // other cleanup
}
```

## Testing strategy
- Unit-test Views: construct view classes and assert node structure and CSS classes. No JavaFX thread? Use TestFX or start JavaFX toolkit via Platform.startup once in tests; or use headless testing frameworks.
- Unit-test Controllers: inject a mock Model (plain POJO) and either use a lightweight headless JavaFX test harness (TestFX) or test handler logic that doesn't require creating Stage (many controllers can be tested by exposing internal methods or using dependency injection for Views).
- Keep logic that can be tested off the FX thread; isolate as much as possible.

## Alternatives & variations
- FXML approach: let FXML describe layout and use @FXML-annotated controller classes. FXML controllers are still MVC Controllers; you should keep model interactions in controller code and keep FXML views passive.
  - Advantage: declarative layouts, SceneBuilder compatibility.
  - Disadvantage: slightly more indirection for programmatic composition and DI.
- Dependency Injection: use a simple factory or a DI framework (Guice, Dagger) to inject Model into Controller and Controller into higher-level app. For small projects, constructor injection is sufficient.

## Common pitfalls and how to avoid them
- Pitfall: View methods perform business logic — Fix: move logic to Controller/Model.
- Pitfall: Mutating UI from background thread — Fix: use Task.setOnSucceeded or Platform.runLater.
- Pitfall: Controller and View tightly coupled via subclassing JavaFX nodes — Fix: prefer composition and small interfaces (e.g., expose Node getRoot()).
- Pitfall: Not cleaning listeners → memory leaks — Fix: implement dispose/unbind patterns.

## Example Main bootstrap
Keep Main minimal and deterministic:
```
package app;

import controller.MainController;
import javafx.application.Application;
import javafx.stage.Stage;
import model.GameModel;

public class MainApp extends Application {
  @Override
  public void start(Stage stage) {
    GameModel model = new GameModel(); // pure model
    MainController controller = new MainController(model);
    controller.show(stage);
  }

  public static void main(String[] args) { launch(args); }
}
```

## Best practices summary (concise list)
- Views: produce Nodes, no handlers that call Model.
- Controller: compose Views, register handlers, call Model, coordinate navigation.
- Model: pure logic; use Properties for observability.
- Threading: keep UI ops on FX thread; use Task for background work.
- Lifecycle: implement cleanup for listeners.
- Testing: inject mocks, test controllers off-FX where possible or use TestFX.

Teacher Tip: When unsure where code belongs, ask: “Does this line change presentation (layout, style), control flow (navigation, event handling), or domain state?” Put it in View, Controller, or Model respectively.
